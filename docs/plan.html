Warden: local AI review desk for merge requests

A macOS desktop app that watches our GitLab (and later GitHub) projects, checks out each new merge request locally, runs our tests, has your local Claude review the change through a small set of MCP tools, filters the findings through guardrails, and posts line-anchored notes back to the MR. You approve what goes out, or let it post on its own once you trust it.

How a review flows

flowchart LR
  A[Poll GitLab every 2 min] --> B{New MR or new commits?}
  B -- no --> A
  B -- yes --> C[Create worktree at head SHA]
  C --> D[Deterministic checks: semgrep, gitleaks, ruff]
  C --> E[Local CI recipes]
  D --> F[Claude review through MCP tools]
  E --> F
  F --> G[Guardrail filter]
  G --> H{Posting mode}
  H -- Draft --> I[You approve in Warden]
  H -- Assist / Auto --> J[Post notes to MR]
  I --> J
  J --> K[Watch threads, re-review on push]
  1. Detect. The poller lists open MRs per watched project and compares the head SHA with the last reviewed SHA. Draft/WIP MRs and MRs labelled no-ai-review are skipped.
  2. Prepare. A git worktree is created at the MR head under ~/.warden/worktrees/<project>/<iid>, so your own checkout is never touched.
  3. Check. Fast deterministic tools run first (semgrep rules, gitleaks, linters). Their hits are passed to Claude as facts, which keeps it from spending turns rediscovering them.
  4. Test. CI recipes from .warden.yml run in parallel: lint, unit tests on a test site, optionally real .gitlab-ci.yml jobs through gitlab-ci-local.
  5. Review. Claude gets the diff, the repo rules and the CI results, explores context with read-only tools, and records each issue through review.add_finding. It has no tool that writes to GitLab.
  6. Filter and post. The guardrail engine validates every finding (anchor inside the diff, confidence, severity, duplicates, note budget). Survivors go to your approval queue or straight to the MR, depending on the mode.
  7. Follow up. On the next push only the new commits are reviewed. Findings whose lines were fixed are resolved automatically; open threads stay open.

Key rule: Claude proposes, Warden disposes. The GitLab token lives in the macOS Keychain and is only used by the Poller and Poster. Claude reads code and records findings into SQLite; it can never post, approve, merge or push. That single boundary is what makes auto-posting safe to switch on later.

Connecting to your Claude Code subscription

  • Engine: Warden spawns the claude CLI you already use, in headless mode, with the MR worktree as its working directory. No Agent SDK, no API key, no per-token billing.
  • Auth: the CLI's existing subscription login (Pro / Max). Warden strips ANTHROPIC_API_KEY and ANTHROPIC_AUTH_TOKEN from the child environment, because either one silently switches the CLI to API billing.
  • Tools: Warden's MCP server is passed with --mcp-config and --strict-mcp-config, so Claude sees only Warden tools plus read-only built-ins.
  • Limits: reviews draw on your plan's usage window, so Warden caps reviews per hour and pauses the queue near the limit instead of tracking dollars.
  • Model: --model opus, --max-turns 30, 10 minute timeout per review.
claude -p "$REVIEW_PROMPT" \
  --output-format stream-json --verbose \
  --mcp-config ~/.warden/mcp.json --strict-mcp-config \
  --allowedTools "mcp__warden__*" Read Grep Glob \
  --disallowedTools Bash Edit Write WebFetch WebSearch \
  --model opus --max-turns 30

The same MCP server, outside the app

  • Warden also exposes its tools as a standalone MCP server on localhost (streamable HTTP).
  • Add it to Claude Code or Claude Desktop and ask "review !31 in entries_crm" or "why did unit fail on !28" from chat.
  • Chat sessions get the same read-only tool set. Posting still goes through the Warden queue.

Guardrails in layers

Each layer catches something the one before cannot. Layers 1, 2 and 4 are plain code, so they hold even if the model misbehaves or the MR contains prompt-injection text.

LayerWhat it doesEnforced by
1 · InputMR title, description and code are wrapped as untrusted data. Secrets are redacted with gitleaks before anything is sent. Lockfiles, minified and generated files are skipped. Large diffs are split per file.Warden main process
2 · Agent sandboxTool allowlist: Warden MCP tools plus Read/Grep/Glob scoped to the worktree. No Bash, no web, no write tools. A PreToolUse hook in a Warden-only settings file rejects any path outside the worktree. Turn and time caps per review.CLI --allowedTools, --disallowedTools, --strict-mcp-config, --max-turns, hook
3 · Review rulesRepo rules from .warden.yml go into the system prompt. Each finding must cite a rule id or concrete evidence. Deterministic rules (semgrep, regex) run outside the model and are passed in as facts.Prompt + structured output schema
4 · Output validationSchema check; file and line must sit on a changed line of the diff; confidence and severity thresholds; per-MR note budget; dedupe against existing discussions by content hash; tone check (no "LGTM", no speculation without evidence).Guardrail engine (pure functions, unit tested)
5 · Posting policyDraft, Assist or Auto per project. Global pause switch. Never approves, merges or changes labels except ai-reviewed. Posts as a bot user. Rate limit on notes per hour.Poster
6 · AuditEvery run stores prompt, tool calls, cost, raw findings, guardrail decisions and what was posted, so a bad note can be traced and the rule fixed.SQLite + History screen

Repo rules file

Lives in each repo so rules are reviewed like code. Warden adds local overrides on top.

# .warden.yml
version: 1
review:
  focus: [security, correctness, frappe-permissions, performance]
  ignore_paths: ["yarn.lock", "**/*.min.js", "**/dist/**"]
  max_notes: 10
  min_confidence: 0.7
  severity_floor: minor
  nits: false

rules:
  - id: FR-001
    title: Whitelisted methods must check permissions
    applies_to: "**/*.py"
    instruction: >
      Any @frappe.whitelist() function that reads or writes documents must call
      frappe.has_permission, doc.check_permission or frappe.only_for first.
    severity: major
  - id: FR-002
    title: No string-formatted SQL
    semgrep: rules/frappe-sql-fstring.yml     # deterministic, no model call
    severity: blocker

ci:
  recipes:
    - name: lint
      run: ruff check {changed_py} && npx eslint {changed_ts}
    - name: unit
      run: bench --site crm_test.localhost run-tests --app entries_crm --failfast
      cwd: ../..            # bench root
      timeout: 15m
    - name: gitlab-ci
      use: gitlab-ci-local
      jobs: [build]

posting:
  mode: assist
  auto_post: { severities: [blocker, major], min_confidence: 0.85 }
  summary_note: true

Finding schema (Claude output)

{
  "file": "entries_crm/api/import_links.py",
  "line": 16,
  "side": "new",
  "severity": "blocker",          // blocker | major | minor | nit
  "category": "security",
  "rule_id": "FR-002",            // or null with evidence filled

MCP tool surface

Small on purpose. Every tool is read-only against the forge; the only writes go to Warden's own database.

Local CI

Isolation

  • One git worktree per MR, pruned after merge or close.
  • Recipes run with tokio::process, a clean env, and a per-job timeout.
  • Optional Docker mode: docker run --network none -v worktree:/src for untrusted forks.

Runners

  • Recipes: any shell command with placeholders like {changed_py}.
  • gitlab-ci-local: runs real .gitlab-ci.yml jobs on this Mac.
  • act: same for GitHub Actions when GitHub lands.

Frappe specifics

  • Unit tests need a site: one dedicated test site per bench (e.g. crm_test.localhost).
  • Worktree is symlinked into the bench apps folder only for the test run, then restored, so the dev site keeps working.
  • One bench test run at a time per bench (queue lock).

Reporting

  • Results table goes into the summary note.
  • Failures are handed to Claude with the diff to explain and anchor.
  • Optional: set a GitLab commit status warden/local-ci (off by default).

Risks

Noisy reviews

Too many low-value notes and people stop reading. Mitigated by the note budget, confidence floor, nits off, and starting in Draft mode.

Prompt injection in MRs

An MR description or code comment tries to steer the reviewer. Mitigated by untrusted wrapping, no write tools, and code-level output checks.

Bench test side effects

Running tests can disturb the dev site. Mitigated by a separate test site, per-bench lock and restoring the apps symlink after each run.

Hitting plan limits

Big MRs or a burst of pushes can use up the usage window. Mitigated by the hourly cap, pause threshold, per-file diff splitting, and reviewing only new commits on re-push. Each developer runs Warden on their own plan rather than one shared login.

Line anchors drifting

GitLab rejects positions that are off the diff. Mitigated by validating each anchor against the parsed diff before posting, with fallback to a file-level note.
